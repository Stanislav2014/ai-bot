## Goal

Закрыть **третий канал утечки** `TELEGRAM_BOT_TOKEN`, обнаруженный при manual re-verify O-02.1. Hotfix O-02.1 чистил `bc["data"]["url"]`, но дефолтный `httpx`-логгер пишет URL в **plain-text** `bc["message"]`:

```
"HTTP Request: POST https://api.telegram.org/bot<TOKEN>/getMe \"HTTP/1.1 200 OK\""
```

Это category=`httpx` (lowercase, через stdlib logging), отличается от `httplib` (HttpxIntegration сам). Stan увидел токен в Sentry breadcrumbs после деплоя O-02.1 фикса.

## Scope

### In scope
- `_scrub_breadcrumb_message`: всегда применять `_scrub_url` к строке (даже если это не JSON), JSON-парсинг остаётся для sensitive keys
- `_before_breadcrumb`: дополнительно вызвать `_scrub_breadcrumb_message` (раньше делал только URL в data)
- `_before_send`: scrub `event["logentry"]["message"]` если есть
- 4 новых теста

### Out of scope
- Recursive deep scrub всех str values в event — слишком агрессивно, может ломать non-Telegram URLs
- Disable httpx default logger целиком — теряем полезную диагностику
- Создать отдельную задачу типа O-03 «PII deep audit» — это уже паттерн повторяющихся хотфиксов

## Design notes

**Почему `_scrub_url` применяется к message всегда:**
- Regex `_TG_TOKEN_RE` matches только `/bot<token>/` pattern — false positives крайне маловероятны
- Стоимость regex на каждый breadcrumb message — micro (короткие строки)
- Универсальная защита: любой логгер, который положит URL в message, защищён

**Почему оба `_before_breadcrumb` И `_before_send` делают scrub:**
- `before_breadcrumb` — первая линия (до scope), но только для новых breadcrumbs
- `before_send` — последняя линия (перед отправкой), ловит accumulated breadcrumbs + сам event payload
- Defense in depth: если один сломается, второй покроет
